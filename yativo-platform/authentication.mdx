This guide is for developers who call the Yativo API from their own servers.
It explains how to authenticate with a **team API key and secret**, how keys
relate to your **team** (owner, members, roles), how to manage keys, and how
to move off the old `account_id` + `app_secret` login, which is being
deprecated.

- [IP Whitelisting](/yativo-platform/security/ip-whitelisting): allowed-IP rules (required on production, optional on sandbox).
- [Passkey Login](/yativo-platform/security/passkey-authentication): how people sign in to the dashboard.
- [Team Functionality](/yativo-platform/security/team-management): the full roles and permissions model.

## Deprecation notice: the legacy login

The old way to authenticate server-to-server was:

1. Call `GET/POST /api/v1/generate-secret` to get an `app_secret`.
2. Call `POST /api/v1/auth/login` with `account_id` (your base64-encoded
   email) and `app_secret` to get a JWT.
3. Send that JWT as `Authorization: Bearer <token>` and refresh it with
   `GET /api/v1/auth/refresh-token`.

**This flow is deprecated.** Replace it with a team API key.

| Date | What changes |
|---|---|
| Now | Team API keys are available. Use them for all new integrations. |
| **Since 15 October 2026** | Bearer tokens are only accepted from Yativo web apps (by default any `https://*.yativo.com` origin). A token from `POST /auth/login` sent from your servers, a script, or Postman gets `403`. The legacy flow no longer works for integrations. API keys keep working only from IPs on their whitelist. |
| Now | A token is read only from the `Authorization: Bearer` header. A token in the URL (`?token=`), the request body or a cookie is ignored. If you send API key headers and a bearer token together, the bearer token is ignored and the API key is used. |
| Later (date to be announced) | `POST /api/v1/auth/login` (with `account_id` / `app_secret`) and `/api/v1/generate-secret` are removed. |

See [Migrating from the legacy login](#migrating-from-the-legacy-login).

> **Why the change?** The `app_secret` was your account password: generating
> a new one replaced your password, and anyone holding it could sign in as
> you. API keys are separate from any person's login, can be revoked one at
> a time, are tied to allowed IPs, and never expire on their own.

## Environments

| Environment | Base URL |
|---|---|
| Sandbox | `https://smtp.yativo.com/api/v1` |
| Production | `https://api.yativo.com/api/v1` |

Sandbox and production keys are separate. A key created in one environment
doesn't work in the other.

## Which credential to use

| You are building... | Use | Guide |
|---|---|---|
| A backend, job, or script that calls Yativo | **Team API key** (`X-Api-Key` + `X-Api-Secret`) | This guide |
| The Yativo dashboard or a person signing in | Email one-time code or **passkey**, which return a bearer token that only works in the dashboard | [Passkey Login](/yativo-platform/security/passkey-authentication) |
| An AI assistant (Claude, Cursor, and so on) | MCP OAuth sign-in, or a team API key | [MCP Server](/yativo-platform/testing/mcp-server) |

## How API keys work

An API key is a pair of values that belong to a **team** (your business
account):

| Value | Header | Format | Visibility |
|---|---|---|---|
| **API key** | `X-Api-Key` | `yativo_pk_` + 32 characters | Public identifier. Shown in the dashboard at any time. |
| **API secret** | `X-Api-Secret` | `yativo_sk_` + 40 characters | Shown **once**, when the key is created. Only a hash is stored, so it can't be retrieved later. |

Send both headers on any `/api/v1` endpoint that needs a signed-in account.
The request then runs as the **team owner's account**, scoped to that team.
No login call, no token, and no refresh are needed, and keys don't expire.
They work until they're revoked.

Each request is checked in this order:

1. If neither header is present, the request is treated as a normal
   dashboard request (bearer token).
2. If only one header is present, the request fails with `401`.
3. The key must exist and not be revoked, and the secret must match (`401`
   otherwise).
4. On production the request must come from one of the key's allowed IPs.
   Sandbox may omit a whitelist; if one is set it is still enforced. See
   [IP Whitelisting](/yativo-platform/security/ip-whitelisting).

Don't send an `Authorization: Bearer` header together with the key and
secret. The key pair on its own is enough.

> API keys are for **server-to-server** use only. Never put them in a
> browser, a mobile app, or any code your end users can see.

## Quick start

### 1. Create a key

In the dashboard, go to **API Keys**, enter a label (for example
"Production backend") and the public IPs of the servers that will use the
key. Production keys need at least one IP; sandbox keys may omit the list.
See [finding your server's IP](/yativo-platform/security/ip-whitelisting#find-your-servers-public-ip).

Copy the **secret** right away and store it in your secrets manager or
server environment variables. If you lose it, create a new key and revoke
the old one.

### 2. Call the API

```http
X-Api-Key: yativo_pk_9f1c2a...
X-Api-Secret: yativo_sk_3e7bd1...
Accept: application/json
```

#### cURL

```bash
curl https://api.yativo.com/api/v1/profile \
  -H "X-Api-Key: $YATIVO_API_KEY" \
  -H "X-Api-Secret: $YATIVO_API_SECRET" \
  -H "Accept: application/json"
```

#### Node.js

```js
import axios from 'axios';

const yativo = axios.create({
  baseURL: 'https://api.yativo.com/api/v1',
  headers: {
    'X-Api-Key': process.env.YATIVO_API_KEY,
    'X-Api-Secret': process.env.YATIVO_API_SECRET,
    Accept: 'application/json',
  },
});

const { data } = await yativo.get('/profile');
```

#### PHP (Laravel HTTP client)

```php
$response = Http::baseUrl('https://api.yativo.com/api/v1')
    ->withHeaders([
        'X-Api-Key'    => env('YATIVO_API_KEY'),
        'X-Api-Secret' => env('YATIVO_API_SECRET'),
    ])
    ->acceptJson()
    ->get('/profile');
```

#### Python

```python
import os, requests

session = requests.Session()
session.headers.update({
    "X-Api-Key": os.environ["YATIVO_API_KEY"],
    "X-Api-Secret": os.environ["YATIVO_API_SECRET"],
    "Accept": "application/json",
})

resp = session.get("https://api.yativo.com/api/v1/profile")
```

### 3. Check your setup

Call the check endpoint from the server that uses the key. It confirms the
key works and shows whether your server's IP passes the key's whitelist:

```bash
curl -s https://api.yativo.com/api/v1/ip-whitelist/check \
  -H "X-Api-Key: $YATIVO_API_KEY" \
  -H "X-Api-Secret: $YATIVO_API_SECRET"
```

See [IP Whitelisting → Check your IP](/yativo-platform/security/ip-whitelisting#check-your-ip) for
the response.

## Migrating from the legacy login

| | Legacy (deprecated) | Team API key |
|---|---|---|
| Get credentials | `generate-secret` returns an `app_secret` (this also resets your password) | Create a key in the dashboard |
| Authenticate | `POST /auth/login` with `account_id` + `app_secret`, then `Authorization: Bearer <JWT>` | `X-Api-Key` + `X-Api-Secret` on every request |
| Expiry | Token expires, and is also cut off after 5 minutes without a request | Never expires. Works until revoked |
| Refresh | `GET /auth/refresh-token` | Not needed |
| Revoke | Change your password | Revoke the single key |
| IP restriction | None | Required whitelist |
| Works from servers after 15 Oct 2026 | **No** | Yes |

Steps:

1. **Find your egress IPs.** Run `curl https://checkip.amazonaws.com` on each
   server that calls Yativo. See
   [IP Whitelisting](/yativo-platform/security/ip-whitelisting#find-your-servers-public-ip).
2. **Create a key** in the dashboard with those IPs. Use one key per system
   so you can revoke them separately.
3. **Store** the key and secret as `YATIVO_API_KEY` and `YATIVO_API_SECRET`
   in your secrets manager.
4. **Change your HTTP client.** Remove the login call, the token cache, the
   refresh logic, and the `Authorization` header. Add the two key headers to
   every request.
5. **Test in sandbox**, then call `GET /ip-whitelist/check` from each
   production server and make sure `key_usage.allowed_server` is `true`.
6. **Deploy to production** with API keys on every server — bearer tokens from scripts have been rejected since 15 October 2026.
7. **Delete the old `app_secret`** from your configuration and secrets
   manager. It is your account password, so don't leave copies around.
   Nothing needs it after the migration.

Request and response bodies are the same for both methods. Only the
authentication headers change.

## API keys and your team

Every business account is a **team** with one **owner** and any number of
invited **members**. See [Team Functionality](/yativo-platform/security/team-management) for the
full model.

**Keys belong to the team, not to the person who created them.** A key keeps
working if its creator leaves the team. The list shows who created each key.

**Keys act as the team owner.** A request made with a key has the owner's
access to the team's business account. Endpoints that change how a person
signs in (passkeys, two-factor authentication, PIN, app secret) or delete the
account reject API keys with `403`. Team roles (admin, finance, viewer, and
so on) do **not** limit what a key can do. That's why the permission to
create keys should only go to people you'd trust with the owner's access.

**Who can manage keys:**

| Action | Permission | Default roles that have it |
|---|---|---|
| View keys | `team.api-keys.view` | owner, admin, viewer |
| Create a key | `team.api-keys.create` | owner, admin |
| Change a key's allowed IPs | `team.api-keys.create` | owner, admin |
| Revoke a key | `team.api-keys.revoke` | owner, admin |

The owner always has every permission. The owner can change which roles have
these permissions on the **Roles** page.

**Team members in the dashboard.** When a member signs in to the dashboard,
their requests act on the team's account, limited by their role:

- A member can only use an endpoint if their role has the matching
  permission. Otherwise the API returns
  `403 You do not have permission to perform this action.`
- Endpoints that aren't mapped to a permission are blocked for members:
  `403 Your team role does not have access to this action.`
- The `viewer` role can only make `GET` requests:
  `403 Your team role is read-only; only GET requests are allowed.`
- Some endpoints always act on the member's own account, never the team
  owner's: PIN, two-factor authentication, passkeys, profile, account
  deletion, and the `/teams/{teamId}/...` endpoints.

## Managing keys (dashboard API)

These endpoints power the **API Keys** page in the dashboard. They're
documented for dashboard developers. **They only work from the dashboard.**
Since 15 October 2026, a request made with an API key, or from anywhere other
than `https://app.yativo.com`, gets
`403 IP whitelists and API keys can only be managed from the Yativo dashboard.`
You can't create or change keys with a key.

All paths are relative to `/api/v1` and use the signed-in user's bearer
token:

```http
Authorization: Bearer <ACCESS_TOKEN>
```

Calls must be made from the dashboard page in the browser, so the `Origin`
(or `Referer`) header shows `https://app.yativo.com`. Don't send them
through a server-side proxy that drops those headers.

Success responses use the standard envelope. The HTTP status of a success is
`200` even when the body says `"status_code": 201`, so check `status` in the
body. Errors come back with their real HTTP status.

### List keys

```http
GET /teams/{teamId}/api-keys
```

Requires `team.api-keys.view`. The secret is never returned.

```json
{
  "status": "success",
  "status_code": 200,
  "message": "Request successful",
  "data": {
    "api_keys": [
      {
        "id": 4,
        "team_id": 12,
        "created_by": 7,
        "label": "Production backend",
        "key": "yativo_pk_9f1c2a...",
        "allowed_ips": ["203.0.113.10", "203.0.113.0/28"],
        "last_used_at": "2026-09-30T14:12:03.000000Z",
        "revoked_at": null,
        "created_at": "2026-09-01T09:00:00.000000Z",
        "updated_at": "2026-09-30T14:12:03.000000Z",
        "creator": { "id": 7, "name": "Jane Doe", "email": "jane@example.com" }
      }
    ]
  }
}
```

- `allowed_ips` is `null` only on keys created before a whitelist was
  required. Prompt the user to add IPs to these keys.
- `revoked_at` is `null` for active keys. Revoked keys stay in the list.
- `last_used_at` updates every time the key authenticates a request.

### Create a key

```http
POST /teams/{teamId}/api-keys
Content-Type: application/json

{
  "label": "Production backend",
  "allowed_ips": ["203.0.113.10", "203.0.113.0/28"]
}
```

Requires `team.api-keys.create`.

| Field | Type | Required | Notes |
|---|---|---|---|
| `label` | string | yes | Up to 255 characters. |
| `allowed_ips` | string[] | yes | 1 to 50 IPv4/IPv6 addresses or CIDR ranges, no duplicates. See [whitelist rules](/yativo-platform/security/ip-whitelisting#whitelist-rules). |

```json
{
  "status": "success",
  "status_code": 201,
  "message": "Request successful",
  "data": {
    "api_key": {
      "id": 5,
      "label": "Production backend",
      "key": "yativo_pk_9f1c2a...",
      "allowed_ips": ["203.0.113.10", "203.0.113.0/28"],
      "last_used_at": null,
      "revoked_at": null,
      "...": "..."
    },
    "secret": "yativo_sk_3e7bd1...",
    "message": "Save this secret now — it will not be shown again."
  }
}
```

This is the **only** response that contains the secret. Show it once with a
copy button and a clear warning, and don't store it in the browser.

### Change a key's allowed IPs

```http
PUT /teams/{teamId}/api-keys/{keyId}/allowed-ips
Content-Type: application/json

{
  "allowed_ips": ["203.0.113.10", "203.0.113.25"]
}
```

Requires `team.api-keys.create`. The list **replaces** the current one. The
key and secret don't change. A revoked key returns
`422 This API key has been revoked.`

### Revoke a key

```http
DELETE /teams/{teamId}/api-keys/{keyId}
```

Requires `team.api-keys.revoke`. The key stops working immediately. This
can't be undone, so ask the user to confirm first.

```json
{
  "status": "success",
  "status_code": 200,
  "message": "Request successful",
  "data": { "message": "API key revoked successfully" }
}
```

### Suggested dashboard UX

1. Check the user's permissions first with
   `GET /teams/{teamId}/members/{userId}/has-permission/{permission}` and
   hide the list, the **Create key** form, and the **Revoke** buttons
   accordingly.
2. Make the allowed-IPs field required. Pre-fill it with the value of
   `tested_ip` from `GET /ip-whitelist/check` only if the user confirms it's
   their server's IP, not their own browser's.
3. Show a warning badge on keys whose `allowed_ips` is `null` and link to
   **Edit allowed IPs**.
4. Show an **Active** / **Revoked** badge from `revoked_at`, and hide
   **Revoke** on revoked keys.

## Errors

Errors use the standard envelope:

```json
{
  "status": "failed",
  "status_code": 401,
  "message": "Request failed.",
  "data": { "error": "Invalid or revoked API credentials." }
}
```

| HTTP | `data.error` | Cause | Fix |
|---|---|---|---|
| 401 | `Both X-Api-Key and X-Api-Secret headers are required.` | Only one of the two headers was sent. | Send both. |
| 401 | `Invalid or revoked API credentials.` | Unknown key, wrong secret, or revoked key. | Check the values, or create a new key. |
| 401 | `This API key's team has no owner account.` | The team's owner account no longer exists. | Contact support. |
| 401 | `This API key has no whitelisted IP addresses. ...` | Production request with no allowed IPs on the key. | [Add IPs](/yativo-platform/security/ip-whitelisting#change-a-keys-allowed-ips). |
| 403 | `Invalid credentials.` | Request came from an IP not on the whitelist. | [Add your egress IP](/yativo-platform/security/ip-whitelisting#find-your-servers-public-ip). |
| 403 | `Bearer tokens are only accepted from the Yativo dashboard. ...` | A bearer token was used outside the dashboard (since 15 October 2026). | Use an API key. |
| 403 | `This endpoint cannot be used with an API key. ...` | The endpoint changes how a person signs in (passkeys, 2FA, PIN, app secret) or deletes the account. | Do it in the dashboard. |
| 403 | `IP whitelists and API keys can only be managed from the Yativo dashboard.` | A key or whitelist change came from an API key or from outside the dashboard (since 15 October 2026). | Make the change in the dashboard. |
| 403 | `You do not have permission to perform this action.` | The signed-in member's role lacks the permission. | Ask the team owner to change your role. |
| 422 | Validation errors | Missing `label`, or invalid `allowed_ips`. | Correct the request. |

## Rotating and revoking keys

**To rotate a key:**

1. Create a new key with the same allowed IPs.
2. Deploy the new key and secret to your servers.
3. Confirm that traffic works: the old key's `last_used_at` stops changing.
4. Revoke the old key.

**If a secret leaks, revoke that key immediately.** It acts with the team
owner's access, so revoking it is faster and more effective than changing
anyone's password.

## Security best practices

- Keep the secret in a secrets manager or environment variable. Never commit
  it to source control and never log it.
- Always use HTTPS.
- Use a separate key for each system or environment, so you can revoke one
  without affecting the others.
- Whitelist the fewest IPs you can: single addresses rather than ranges.
- Only give `team.api-keys.create` to people you'd trust with the owner's
  access, because a key has that access.
- Review `last_used_at` regularly and revoke keys that are no longer used.

## FAQ

**Can I use a key from a browser or mobile app?**
No. The secret would be visible to your users. Call Yativo from your backend,
and have your apps talk to your backend.

**Can I keep using `POST /auth/login` with my `app_secret`?**
No for integrations. Since 15 October 2026 the token it returns is rejected
outside the dashboard. The endpoint itself will be removed later.

**Do keys expire?**
No. A key works until it's revoked.

**Can a key be limited to certain actions, like a team role?**
A key has the team owner's access to the business account. Limit who can
create keys, and use a separate key per system. Keys can never change how
anyone signs in (passkeys, 2FA, PIN) or delete the account.

**Can I create or revoke keys with a key?**
No. Since 15 October 2026 that's only possible in the dashboard.

**My key returns 401 `Invalid or revoked API credentials.`**
Check that both headers are for the same key and environment (sandbox or
production), and that the key hasn't been revoked. If you've lost the secret,
create a new key.
