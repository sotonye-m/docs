## How webhooks work

1. You register a single HTTPS URL on your account. Every event is sent to that one URL.
2. When an event occurs, Yativo sends an `HTTP POST` request to your URL with a JSON body describing the event.
3. Your endpoint verifies the request signature, processes the event, and returns a `2xx` status code quickly.

| | |
|---|---|
| HTTP method | `POST` |
| Content type | `application/json` |
| Signature header | `Signature` |
| Signature algorithm | `HMAC-SHA256` (hex-encoded) |
| Timeout | Respond within a few seconds |
| Success criteria | Any `2xx` HTTP status code |

> **Note:** the signature header is named `Signature`, not `X-Signature` or `X-Webhook-Signature`.

## Registering your endpoint

All webhook management endpoints live under `/v1/business/webhook` and require your API credentials:

```
X-Api-Key: <your-api-key>
X-Api-Secret: <your-api-secret>
```

### Create or replace your webhook

```
POST /v1/business/webhook
```

| Field | Type | Required | Description |
|---|---|---|---|
| `url` | string (URL) | yes | The HTTPS endpoint that will receive events |

```bash
curl -X POST https://api.yativo.com/api/v1/business/webhook \
  -H "X-Api-Key: $YATIVO_API_KEY" \
  -H "X-Api-Secret: $YATIVO_API_SECRET" \
  -H "Content-Type: application/json" \
  -d '{ "url": "https://example.com/webhooks/yativo" }'
```

**Response `200 OK`**

```json
{
  "status": "success",
  "status_code": 200,
  "message": "Request successful",
  "data": {
    "id": "b1a7c6e0-4b2a-4c39-9c2e-3a2f6a8e9d10",
    "user_id": 1024,
    "url": "https://example.com/webhooks/yativo",
    "secret": "<your-webhook-secret>",
    "events": "general",
    "created_at": "2026-09-07T14:32:10.000000Z",
    "updated_at": "2026-09-07T14:32:10.000000Z"
  }
}
```

- **One endpoint per account.** Calling `POST /v1/business/webhook` again replaces your URL **and issues a new secret**. It doesn't add a second endpoint.
- Save the `secret` straight away; you need it to verify signatures. Every endpoint below also returns it.
- Every event goes to your URL. There is no per-event subscription, so ignore `event.type` values you don't handle.
- Right after you save a webhook, Yativo sends a [`webhook_updated`](#webhook_updated) test event to the new URL.

### List your webhook

```
GET /v1/business/webhook
```

Returns the same webhook object as above, inside a `data` array.

### Update your webhook URL

```
PUT /v1/business/webhook/{id}
```

```json
{ "url": "https://example.com/webhooks/yativo-v2" }
```

Updating the URL keeps your secret unchanged.

### Rotate your signing secret

```
POST /v1/business/webhook/{id}/regenerate-secret
```

Returns the webhook object with a new `secret`. The previous secret stops working immediately, so deploy the new one to your endpoint right away.

### Delete your webhook

```
DELETE /v1/business/webhook/{id}
```

```json
{
  "status": "success",
  "status_code": 200,
  "message": "Request successful",
  "data": { "message": "Webhook deleted successfully" }
}
```

### Error responses

All endpoints above return this shape on failure:

```json
{
  "status": "failed",
  "status_code": 400,
  "message": "Request failed.",
  "data": { "error": "Provided webhook not found!" }
}
```

## Verifying the signature

Every webhook request carries a `Signature` header:

```
Signature: 5f5c1a2e9e0b1a6b3c7d... (hex-encoded HMAC-SHA256)
```

It is computed as:

```
signature = hex( HMAC_SHA256( raw_json_body, your_webhook_secret ) )
```

Recompute it over the **exact raw request body**. Don't re-serialize the parsed JSON, because whitespace or key-order differences will break the match. Compare using a constant-time comparison.

The signed payload has no timestamp, so pair signature checks with idempotency handling (see [Best practices](#best-practices)).

### PHP

```php
$payload = file_get_contents('php://input');
$signature = $_SERVER['HTTP_SIGNATURE'] ?? '';

$expected = hash_hmac('sha256', $payload, $yourWebhookSecret);

if (! hash_equals($expected, $signature)) {
    http_response_code(401);
    exit('Invalid signature');
}

$event = json_decode($payload, true);
```

### Node.js (Express)

```js
const crypto = require('crypto');

app.post('/webhooks/yativo', express.raw({ type: 'application/json' }), (req, res) => {
  const signature = req.header('Signature') || '';
  const expected = crypto
    .createHmac('sha256', process.env.YATIVO_WEBHOOK_SECRET)
    .update(req.body) // raw Buffer, not the parsed object
    .digest('hex');

  const valid =
    signature.length === expected.length &&
    crypto.timingSafeEqual(Buffer.from(signature), Buffer.from(expected));

  if (!valid) {
    return res.status(401).send('Invalid signature');
  }

  const event = JSON.parse(req.body);
  // ... handle event ...
  res.sendStatus(200);
});
```

### Python (Flask)

```python
import hmac
import hashlib

@app.route("/webhooks/yativo", methods=["POST"])
def yativo_webhook():
    raw_body = request.get_data()
    signature = request.headers.get("Signature", "")

    expected = hmac.new(
        YATIVO_WEBHOOK_SECRET.encode(), raw_body, hashlib.sha256
    ).hexdigest()

    if not hmac.compare_digest(expected, signature):
        return "Invalid signature", 401

    event = request.get_json()
    # ... handle event ...
    return "", 200
```

## The payload envelope

Almost every event uses this two-key envelope:

```json
{
  "event.type": "deposit.created",
  "payload": { ... }
}
```

- `event.type` identifies the event, for example `deposit.created`.
- `payload` holds the event data, documented per event below.

The envelope has no delivery id or timestamp, so use fields inside `payload` (such as `id`, `event_id`, `created_at` or `status`) for idempotency and ordering.

> **Gift card events are the one exception.** They have no `event.type`/`payload` wrapper. See [`giftcard.status_changed`](#giftcardstatus_changed-different-envelope).

## The customer object

Every event includes a `customer` object, so you never need a second API call to find out whose event it is. It sits inside `payload` (at the top level for gift card events), next to `customer_id`:

```json
{
  "event.type": "virtualcard.topup.completed",
  "payload": {
    "customer_id": "b8d1c6b0-2f3a-4b8e-9d1a-3c5f6e7a8b90",
    "customer": {
      "customer_id": "b8d1c6b0-2f3a-4b8e-9d1a-3c5f6e7a8b90",
      "customer_email": "jane@example.com",
      "customer_name": "Jane Doe",
      "customer_phone": "+15551234567",
      "customer_type": "individual"
    },
    "...": "event-specific fields"
  }
}
```

| Field | Description |
|---|---|
| `customer_id` | Your Yativo customer id. Sent whenever the event relates to a customer. |
| `customer` | The customer's `customer_id`, `customer_email`, `customer_name`, `customer_phone` and `customer_type` (`individual` or `business`). |

`customer` is `null` when the event isn't about one of your customers, for example `user.updated`, `webhook_updated` or a platform-wide method change. Only these five fields are sent; KYC documents and other sensitive data are never included.

> **Changed on 5 October 2026.** The `customer` object is now included on every event, always with the five fields above. Events that previously sent a shorter `customer` object (`virtual_account.*`, `virtual_account.deposit`, `endorsement.updated`) now send the full one.

### `deposit.created` / `deposit.updated`

Sent when a fiat deposit (pay-in) is created and whenever its status changes.

```json
{
  "event.type": "deposit.updated",
  "payload": {
    "id": "5b1e6b2a-df3d-4a9a-8e93-6c9f4a2b7e10",
    "currency": "USD",
    "amount": 500.00,
    "receive_amount": 495.00,
    "amount_paid": 500.00,
    "incomplete_payment": false,
    "deposit_id": "DEP-00A1B2C3",
    "status": "success",
    "transaction_id": "TXN-00123456",
    "idempotency_key": "your-idempotency-key",
    "created_at": "2026-09-07T14:00:00.000000Z",
    "updated_at": "2026-09-07T14:03:12.000000Z",
    "customer_id": "b8d1c6b0-2f3a-4b8e-9d1a-3c5f6e7a8b90",
    "customer": {
      "customer_id": "b8d1c6b0-2f3a-4b8e-9d1a-3c5f6e7a8b90",
      "customer_email": "jane@example.com",
      "customer_name": "Jane Doe",
      "customer_phone": "+15551234567",
      "customer_type": "individual"
    }
  }
}
```

`status` is one of `pending`, `processing`, `success`, `incomplete`, `failed`, `cancelled` or `expired`.

`amount` is the checkout amount that was requested. Arc Onramp settlements also include:

| Field | Description |
|---|---|
| `amount_paid` | The amount the customer actually paid (crypto that landed on the collection wallet) |
| `incomplete_payment` | `true` when `amount_paid` is less than `amount`. The deposit is credited for what was received and `status` is `incomplete` |
| `receive_amount` | The amount credited to the wallet after fees, based on `amount_paid` |

Those two extra fields are only sent once the payment has settled. The settlement webhook is the one that carries them; a processing update is not sent for that hop.

Deposits with a currency conversion also include `currency_from`, `currency_to`, `amount_from`, `amount_to` and `deposit_currency`. Only these fields and the ones above are sent.

    "updated_at": "2026-09-07T13:05:44.000000Z",
    "beneficiary": {
      "nickname": "John's account",
      "currency": "USD",
      "payment_data": {
        "account_number": "0001234567",
        "bank_name": "Example Bank",
        "account_holder_name": "John Doe"
      }
    },
    "customer_id": "b8d1c6b0-2f3a-4b8e-9d1a-3c5f6e7a8b90",

### RFI events (`rfi.created`, `rfi.updated`, `rfi.response_required`)

Sent when Yativo records a **compliance request for information** on a customer or transaction tied to your account. Payloads do **not** include upstream provider names, provider-side ids, or provider dashboard URLs.

| Event | When |
|---|---|
| `rfi.created` | A new RFI is recorded for your business |
| `rfi.updated` | Status changes (for example moved to review or closed) |
| `rfi.response_required` | Open and waiting on your team (`status` is `action_required`) |

A new RFI that already needs your action may send **`rfi.created`** and **`rfi.response_required`** in quick succession. Use `payload.id` (Yativo RFI id) for idempotency.

Sandbox: `POST /v1/demo/webhook/rfi` (optional body `event`: `rfi.created`, `rfi.updated`, `rfi.response_required`).

### Virtual card events (`virtualcard.*`)

On sandbox you can send any of these events with `POST /api/v1/demo/webhook/virtualcard` or `POST /api/v1/demo/webhook/{event}` — see [Testing your integration on sandbox](#testing-your-integration-on-sandbox). To simulate a charge that is stored on the card, use [Testing on sandbox](/yativo-platform/testing/sandbox-testing).

Every virtual card payload includes:

- `event_id`: unique per event and identical on every redelivery of it. Use it to deduplicate.
- `card_id`: the card id returned when you created the card, which you pass to the card endpoints.
- `customer_id` and `customer`: the cardholder (see [The customer object](#the-customer-object)).

Amounts are decimal USD (`4.5` means $4.50).

> **Changed on 5 October 2026.** Virtual card events used to arrive with no envelope, with amounts in cents, and with camelCase fields such as `cardId`. They now use the standard envelope, snake_case fields, decimal amounts and the `customer` object. The success events were also renamed: `.success` is now `.completed` (`.complete` for KYC). If you parsed the old shape, update your handler.

#### KYC

| Event | Sent when |
|---|---|
| `virtualcard.user.kyc.pending` | The cardholder's verification was received and is under review. This is not a final result. |
| `virtualcard.user.kyc.complete` | Verification passed. You can now create a card for this customer. |
| `virtualcard.user.kyc.failed` | Verification was rejected. Resubmit only after the customer fixes what `rejection_details` describes. |

  "event.type": "virtualcard.user.kyc.failed",
  "payload": {
    "event_id": "6f1c2a9e-4b7d-5e8f-9a0b-1c2d3e4f5a6b",
    "customer_id": "b8d1c6b0-2f3a-4b8e-9d1a-3c5f6e7a8b90",

      {
        "code": "UNSATISFACTORY_PHOTOS",
        "message": "The document or its details could not be read clearly. Please upload a sharper photo."
      }
    ],
    "customer": {
      "customer_id": "b8d1c6b0-2f3a-4b8e-9d1a-3c5f6e7a8b90",

      "customer_name": "Jane Doe",
      "customer_phone": "+15551234567",
      "customer_type": "individual"
    }

}
```

`kyc_status` is `under_review`, `approved` or `rejected`. Show `rejection_details[].message` to your customer and branch your own logic on `code`.

#### Card lifecycle

| Event | Sent when | Effect on your USD wallet |
|---|---|---|
| `virtualcard.created.completed` | The card is issued and ready to use. | None |
| `virtualcard.created.failed` | Issuing the card failed after it was accepted. | The creation fee, top-up fee and opening balance are refunded. |
| `virtualcard.regularized` | A card recovered from an indeterminate state. `status` is its new status, usually `active`. | None |
| `virtualcard.expiration` | The card reached its expiry date. `expired_at` is included. | None |
| `virtualcard.contactless.activation` | Contactless payments were activated on the card. `activated_at` is included. | None |
| `virtualcard.terminated.refund` | The card was terminated and its remaining balance was returned. | The remaining balance (`amount`) is credited. |
| `virtualcard.transaction.terminated.refund` | A refund was posted as part of terminating the card. | Credited, but only once per card across both termination events. |

#### Card transactions

These events report spending on the card balance. Apart from the fees noted below, they don't move money in your wallet.

| Event | Sent when |
|---|---|
| `virtualcard.transaction.authorization` | A purchase was authorized. Settlement follows. |
| `virtualcard.transaction.settlement` | An authorized purchase was settled by the merchant. |
| `virtualcard.transaction.debit` | A settled debit on the card. |
| `virtualcard.transaction.pre-auth.approved` | A pre-authorization hold was placed, for example a hotel or fuel deposit. |
| `virtualcard.transaction.contactless` | A tap-to-pay payment. `transaction_type` is `contactless_pending` or `contactless_settled`. |
| `virtualcard.transaction.credit` | A credit was posted to the card, such as an adjustment. |
| `virtualcard.transaction.refund` | A merchant refund. `transaction_type` is `refund_authorization` or `refund_settled`. |
| `virtualcard.transaction.reversed` | An authorization was reversed before settlement, and the amount returned to the card. |
| `virtualcard.transaction.verification` | A zero-amount card check, for example when the card is saved with a merchant. |
| `virtualcard.transaction.crossborder` | An international purchase. See below. |

All of them share this payload:

```json
{
  "event.type": "virtualcard.transaction.settlement",
  "payload": {
    "event_id": "8a9b0c1d-2e3f-5a4b-9c6d-7e8f9a0b1c2d",
    "card_id": "c8f1a3b2-9e4d-4f1a-b8c7-2d3e5f6a7b8c",
    "customer_id": "b8d1c6b0-2f3a-4b8e-9d1a-3c5f6e7a8b90",
    "transaction_id": "tx_settle_c3d4e5f6a1b2",
    "reference": "settle_ref_3456cdef",
    "transaction_type": "settlement",
    "status": "completed",
    "amount": 4.5,
    "currency": "USD",
    "narrative": "settlement_at_amazon_com",
    "reason": null,
    "merchant": {
      "name": "amazon_com",
      "mcc": "5942",
      "country": "US"
    },
    "occurred_at": "2026-05-16T15:01:33Z",
    "customer": {
      "customer_id": "b8d1c6b0-2f3a-4b8e-9d1a-3c5f6e7a8b90",
      "customer_email": "jane@example.com",
      "customer_name": "Jane Doe",
      "customer_phone": "+15551234567",
      "customer_type": "individual"
    }
  }
}
```

| Field | Description |
|---|---|
| `transaction_id` | The transaction's id, matching the card transactions endpoint. |
| `reference` | Use it to match an authorization to its settlement or reversal. |
| `transaction_type` | One of `authorization`, `settlement`, `pre_auth_approved`, `authorization_declined`, `refund_authorization`, `refund_settled`, `reversal_settled`, `cross_border_pending`, `cross_border_settled`, `cross_border_reversal`, `contactless_pending`, `contactless_settled`, `verification`. |
| `status` | `completed`, `pending`, `declined`, `terminated` or `failed`. |
| `amount` | Decimal amount. Always `0` for verifications. |
| `merchant` | Merchant name, ISO 18245 category code, and ISO 3166-1 alpha-2 country code. Any field may be `null`. |

Some events fire with several `transaction_type` values. Branch on `event.type` first, then on `transaction_type`.

**Cross-border purchases** send `virtualcard.transaction.crossborder` twice, with the same `reference`:

1. `transaction_type: cross_border_pending`: the cross-border fee. `fee_amount` is included, and that fee is **debited from your USD wallet**. `status` stays `pending` until the purchase settles.
2. `transaction_type: cross_border_settled`: the purchase amount leaves the card balance. There is no wallet movement.

#### Declines

| Event | Sent when | Effect on your USD wallet |
|---|---|---|
| `virtualcard.transaction.declined` | A purchase was declined, for example for insufficient card balance. `reason` explains why. | None |
| `virtualcard.transaction.authorization.failed` | An authorization was rejected, for example for an AVS or CVV mismatch. | None |
| `virtualcard.transaction.declined.frozen` | A charge was declined because the card is frozen. | Your card-decline fee is debited. `fee_amount` is included. |
| `virtualcard.transaction.declined.terminated` | A charge was attempted on a terminated card. | None |
| `virtualcard.transaction.declined.charge` | The card broke the decline rules after repeated declines. | The violation fee (`fee_amount`) is debited. `violation_count` is included. |
| `virtualcard.transaction.issuerexpiration` | A charge was declined because the card has expired. | None |

      "customer_id": "b8d1c6b0-2f3a-4b8e-9d1a-3c5f6e7a8b90",

      "customer_name": "Jane Doe",

For employee balances, `card_id` is `null` and `employee_id` is set, because the balance is shared by all of that employee's cards:

`business_spend_card.terminated`: a card was closed, including the automatic termination after a full-balance withdrawal. The payload has `card_id`, `reason` (for example `balance_withdrawn_in_full`), `customer_id` and `customer`.

`business_spend_card.transaction.disputed`: you raised a dispute on a transaction (`POST /v1/business/spend-card/transactions/{id}/dispute` or `POST /v1/spend/cards/transactions/{transaction_id}/dispute`). The dispute fee has already been charged. The payload has `transaction_id`, `card_id`, `amount`, `currency`, `disputed_at` and `customer`.

`business_spend_card.status_changed`: a card's status changed, for example activated, suspended or replaced:

```json
{
  "event.type": "business_spend_card.status_changed",
  "payload": {
    "card_id": "5e318920-0454-4a8d-bc91-d47cdb82645a",
    "status": "Suspended",
    "event_type": "card.suspended",
    "updated_at": "2026-09-16T13:56:19.000000Z",
    "customer": null
  }
}
```

#### Transaction history, notes and invoices

Every `business_spend_card.transaction.*` event is backed by a transaction record you can fetch, annotate and attach receipts to:

```
GET    /v1/business/spend-card/transactions               # paginated list, filter by ?status= and ?card_id=
GET    /v1/business/spend-card/transactions/{id}           # one transaction, with its notes and invoices
POST   /v1/business/spend-card/transactions/{id}/dispute   # { "reason": "..." }, charges the dispute fee
POST   /v1/business/spend-card/transactions/{id}/notes     # { "note": "..." }
DELETE /v1/business/spend-card/notes/{noteId}
POST   /v1/business/spend-card/transactions/{id}/invoices  # multipart/form-data, field name "invoice"
GET    /v1/business/spend-card/invoices/{invoiceId}/download
DELETE /v1/business/spend-card/invoices/{invoiceId}
```

Invoice uploads accept JPG, PNG or PDF up to 10 MB. Every file is virus-scanned; a file that fails is rejected with `422` and never stored. Files are kept in private storage, and `GET .../invoices/{id}/download` returns one only after confirming you own the transaction.

```json
{
  "status": "success",
  "status_code": 200,
  "message": "Request successful",
  "data": {
    "id": 14,
    "user_id": 1024,
    "file_name": "receipt.pdf",
    "mime_type": "application/pdf",

    "scan_status": "clean",

  }
}
```

## Responding to a webhook

- Return a `2xx` status as soon as you've safely stored or queued the event. Do slow work (calling other APIs, sending emails) afterwards.
- We don't read your response body; an empty `200 OK` is enough.
- A non-`2xx` status, a connection error or a timeout counts as a failed delivery.

## Retries, delivery logs and resending

Failed deliveries are retried with exponential backoff, a few times, after which the event is dropped. Some events are delivered inline with the action that triggered them, so **respond quickly (well under a few seconds)**; a slow endpoint can slow down the API call behind the event.

Every delivery attempt, successful or not, is logged:

```
GET /v1/business/events/all
GET /v1/business/events/show/{eventId}
```

To find the delivery for a specific transaction (for example to resend it):

```
GET /v1/business/events/all?transaction_id=TXN-00123456
GET /v1/business/events/all?type=deposit
GET /v1/business/events/all?type=deposit.updated&transaction_id=TXN-00123456&status=failed
```

| Query | Matches |
|---|---|
| `transaction_id` | `payload.transaction_id`, `payload.id`, `payload.deposit_id`, and the same fields at the top level |
| `type` | Exact `event.type` (or `event` / `event_type`), a family prefix (`deposit` → `deposit.updated`), or card `payload.transaction_type` (`settlement`, `authorization`, …). `event` and `transaction_type` are aliases for `type`. |
| `status` | Delivery result: `success` or `failed` |
| `per_page`, `page` | Pagination. `per_page` defaults to `10`. |

```json
{
  "status": "success",
  "status_code": 200,
  "message": "Records retrieved successfully",
  "data": [
    {
      "id": 981,
      "user_id": 1024,
      "url": "https://example.com/webhooks/yativo",
      "payload": { "event.type": "deposit.updated", "payload": { "...": "..." } },
      "status": "success",
      "status_code": 200,
      "response_body": "",
      "resend": null,
      "created_at": "2026-09-07T14:03:12.000000Z"
    }
  ],
  "pagination": {
    "total": 1,
    "per_page": 15,
    "current_page": 1,
    "last_page": 1,
    "next_page_url": null,
    "prev_page_url": null
  }
}
```

Logged payloads are shown with the fields events carry today, so older entries may show fewer fields than were sent at the time. `GET /v1/business/events/show/{eventId}` returns `404` with `Webhook event not found` when the ID isn't in your log.

### Resending an event

If your endpoint was down or rejected an event, you can redeliver it yourself. To put a **Resend** button on the dashboard delivery log, see [Webhook resend — dashboard UI](/yativo-platform/webhooks/resend).

```
POST /v1/business/events/resend/{eventId}
```

`{eventId}` is the `id` from the delivery log above, **not** an id from inside the event's `payload`.

```bash
curl -X POST https://api.yativo.com/api/v1/business/events/resend/981 \
  -H "X-Api-Key: $YATIVO_API_KEY" \
  -H "X-Api-Secret: $YATIVO_API_SECRET"
```

```json
{
  "status": "success",
  "status_code": 200,
  "message": "Request successful",
  "data": { "message": "Webhook event resend has been queued" }
}
```

- The original payload is resent, signed with your **current** secret.
- It goes to the URL you have registered now, even if you've changed it since.
- Fields that events no longer carry are left out.
- The resend appears as a new entry in the delivery log.
- You can only resend events from your own account.
- We record who resent it, when, and the original device IP (not a Cloudflare hop). That object is on the delivery log as `resend` and is **not** sent to your webhook URL.

```json
"resend": {
  "original_event_id": 981,
  "by": { "id": 12, "name": "Ada Lovelace", "email": "ada@example.com" },
  "at": "2026-10-26T17:42:11+00:00",
  "ip": "181.190.49.51",
  "via": "dashboard"
}
```

`via` is `dashboard`, `api_key`, or `admin`. On the original log, `resend` is the latest redelivery of that event; on the new log row it describes this attempt.

**Errors**

```json
{ "status": "failed", "status_code": 404, "message": "Request failed.", "data": { "error": "Webhook event not found" } }
```

```json
{ "status": "failed", "status_code": 400, "message": "Request failed.", "data": { "error": "No webhook endpoint is configured for your account" } }
```

## Testing your integration on sandbox

To settle a real sandbox payin or payout, credit a virtual account, or
simulate a virtual-card / spend-card charge — so the record exists
afterwards — use the helpers in [Testing on sandbox](/yativo-platform/testing/sandbox-testing).

You can also send sample events to your registered URL without creating real records:

```
POST /api/v1/demo/webhook/{type}
```

`{type}` can be:

- A **legacy slug**: `payin`, `payout`, `virtual_account`, `virtual_account_created`, `virtual_account_updated`, `virtual_account_deleted`, `virtual_card_deposit`, `customer`, `customer_updated`, `endorsement`, `metadata_created`, `metadata_updated`, `webhook_updated`, `giftcard`, `user`, `tracking`, `payin_method_enabled`, `payin_method_disabled`, `payout_method_enabled`, `payout_method_disabled`, `crypto_wallet`, `crypto_deposit`, `wallet_deleted`.
- A **documented event name**, for example `deposit.updated`, `virtual_account.deleted`, `virtualcard.topup.completed`, `business_spend_card.transaction.approved`, `card_checkout.order.paid`.
- A **family alias**, which sends one representative event from that family:
  - `virtualcard` → `virtualcard.topup.completed`
  - `spendcard` (also `spend_card` or `business_spend_card`) → `business_spend_card.created`
  - `card_checkout` → `card_checkout.order.paid`

To pick a specific event when using a family alias, pass `event`:

```bash
curl -X POST https://smtp.yativo.com/api/v1/demo/webhook/virtualcard \
  -H "X-Api-Key: $YATIVO_API_KEY" \
  -H "X-Api-Secret: $YATIVO_API_SECRET" \
  -H "Content-Type: application/json" \
  -d '{ "event": "virtualcard.transaction.settlement" }'
```

For `virtualcard.transaction.contactless`, `.refund` and `.crossborder`, you can also pass `transaction_type` (for example `cross_border_pending` or `contactless_pending`) to choose the variant.

```bash
curl -X POST https://smtp.yativo.com/api/v1/demo/webhook/payin \
  -H "X-Api-Key: $YATIVO_API_KEY" \
  -H "X-Api-Secret: $YATIVO_API_SECRET"
```

The sample events are signed like real ones. For example, `payin` sends `deposit.created` followed by `deposit.updated`. Demo events use sample data, so their `customer` may be `null`. When this account already has a matching record (a virtual card, spend card, customer or checkout order), the sample reuses that id.

## Best practices

- **Verify every signature** before trusting the contents. See [Verifying the signature](#verifying-the-signature).
- **Respond fast, process later.** Return `2xx` immediately and process the event in a background job.
- **Be idempotent.** The same event can arrive more than once. Deduplicate on `event_id` where present, or on the record's id (`id`, `transaction_id`, `deposit_id`).
- **Don't assume ordering.** Events for the same record can arrive out of order, for example `deposit.created` after `deposit.updated`. Use `status` and timestamps, not arrival order.
- **Ignore unknown events.** New `event.type` values are added over time; skip ones you don't recognize instead of failing.
- **Keep your secret safe.** Store it in a secrets manager, never in source control, and rotate it with `regenerate-secret` if it may have leaked.
- **Use HTTPS** for your webhook URL.
